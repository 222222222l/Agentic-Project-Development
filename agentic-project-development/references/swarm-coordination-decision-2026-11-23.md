# Agentic Project Development：何时采用 Swarm 的工程决策树

2026-11-23 · 方法层补充；不新增 Agent 运行时。

## 为什么更新

Swarm 的事件消息、独立 Verifier、成员休眠能改善 **多项任务可并行且易失联** 的情况；但普通代码修复与强串行流程不需要额外协调。现有 Skill 本就以最小可靠流程和经济收益为决策原则，应明确选型门槛。

## 选择流程

1. **冻结终态和验收**：用户要达成什么？验收是否由独立证据支持？
2. **找确定性替代**：能由脚本/规则/单次模型调用完成，优先不派第二个 Agent。
3. **标注依赖和冲突**：只有两个及以上可独立工作项、清晰交接产物、互不冲突的写集合，才进入协作试验。
4. **选最小架构**：单 Agent → 固定 DAG → （测出交接/等待损耗）事件黑板 → （测出调度瓶颈）有限自适应。每级保留退路。
5. **分角色验收**：Worker 提交产物引用；独立 Verifier 使用运行测试和签收证据判定；失败直达责任人，不经多层语言转述。
6. **管理生命周期**：等待以持久事件和条件唤醒为准；不要让闲置 Agent 持续轮询；消息游标不能代表任务已完成。
7. **记录总成本**：除了生成 Token，计入工具、等待、返工、验证、人类介入与新框架维护；同任务配对消融。
8. **结束或回退**：提升未达到预先设定门槛则保留单 Agent / DAG，禁止为了规模感强加组织角色。

## 每张多 Agent 开发卡必须附

- 任务 DAG、读写集合、交接消息 schema、源/目标 Revision、授权边界。
- 事件来源、消费者游标、幂等/重试、失联与重启恢复、待人工节点。
- 验收者身份、独立检查证据、旧版/越权/自评拒绝情况。
- 与单 Agent 同权限/预算/模型的对照，合格产出、完整费用与失败轨迹。
- 可复用架构选择 ADR：为何此时需要 Swarm；为何不继续使用简单方案。

**实施方式**：在现有 Skill 的分工/长任务参考路径中引用本决策树；先做文档与示例，只有真实项目显示选择错误时修改路由器，保留原有 `select_workflow.py` 测试。
